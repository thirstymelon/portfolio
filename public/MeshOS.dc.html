Developer Story

Building MeshOS

01 The Spark
The Spark: When the Infrastructure Dies

Modern mobile communication rests on a fragile assumption: that an unbroken chain of cellular base stations, fiber backhauls, DNS servers, and cloud datacenters will always be standing between you and the person next to you.

During severe weather, grid outages, outdoor expeditions, or natural disasters, that assumption instantly collapses. Your smartphone becomes a glass brick unable to transmit a single byte even to someone just 200 meters down the street.

"What if a handful of $3 ESP32 boards could form their own decentralized, encrypted cellular-independent network and let standard smartphones talk to each other anywhere on Earth?"

That question sparked MeshOS. I set out to build an end-to-end communication system starting from bare-metal 2.4 GHz radio framing on the ESP32 and climbing all the way to native companion applications on iOS, macOS, and Android.

02 Multi-Hop Routing
From ESP-NOW to a Self-Healing Multi-Hop Mesh

Espressif provides ESP-NOW, a connectionless Wi-Fi vendor action frame protocol. It is fast and low-power, but it is strictly single-hop: Node A can only talk to Node B if they are in direct line-of-sight radio range. It is not a mesh network.

To turn ESP-NOW into a resilient multi-hop mesh, I designed a bounded-flooding routing layer with strict loop prevention:

Bounded TTL (Max 7)
Every frame carries a Time-To-Live. Intermediate nodes decrement TTL and drop expired packets to prevent endless propagation.
64-Entry LRU Cache
Nodes maintain a rolling ring buffer of (origin_node_id, sequence_number) pairs. Duplicate frames are dropped in microsecond time.
Randomized Jitter
Forwarding adds 10-50ms of random backoff to desynchronize relay nodes and eliminate catastrophic RF packet collisions.
Persistent Node IDs
Each node generates a cryptographically random 32-bit Node ID stored in Non-Volatile Storage (NVS) across reboots.

If Node B drops out, the packet naturally routes around the failure through Node C. The mesh self-heals dynamically with zero manual routing configuration.

03 Dual-Core FreeRTOS
Firmware Architecture: Dual-Core FreeRTOS

An ESP32 node must juggle two time-critical wireless protocols simultaneously: forwarding high-speed 2.4 GHz ESP-NOW frames and maintaining an active Bluetooth Low Energy connection with a user's phone.

Running both on a single core resulted in dropped BLE packets and radio buffer overflows. I architected the firmware around FreeRTOS task affinity pinned cleanly across both Xtensa LX6 cores:

Core 0: Mesh Router & Radio Stack
Runs mesh_router_task at priority 10. Pulls raw packets from ESP-NOW callbacks, checks duplicate caches, decrypts headers, handles route forwarding, and schedules periodic neighbor beacons at priority 3.
Core 1: NimBLE GATT Companion Host
Runs the lightweight Apache NimBLE stack at priority 9. Manages GATT connections, 512-byte MTU negotiations, client indications, and smartphone notifications without ever stalling radio routing.

Data flows between cores through thread-safe FreeRTOS queues (mesh_tx_queue, ble_rx_queue, ble_tx_queue) protected by mutexes, ensuring rock-solid stability under heavy network traffic.

04 Silicon Security
Zero-Cloud Security: Hardware AES-128-GCM

In an open-air broadcast mesh, anyone with an SDR or a Wi-Fi card can inspect packet bytes. Because MeshOS has no internet connection, it cannot rely on central authentication servers, AWS KMS, or certificate authorities.

I implemented end-to-end security directly in firmware using the ARM PSA Crypto API and the ESP32’s onboard cryptographic hardware engine:

PSA CRYPTO AEAD ENCRYPTION PIPELINE
Raw Payload → Hardware TRNG (12-byte Nonce) → PSA AES-128-GCM → Ciphertext + 16-byte Auth Tag

Each packet is encrypted with a unique 12-byte nonce generated by the ESP32 hardware True Random Number Generator (TRNG). The 16-byte authentication tag guarantees that packets cannot be tampered with or modified in transit.

Intermediate relay nodes route encrypted frames by inspecting unencrypted header metadata without ever possessing the channel keys needed to decrypt message contents.

05 Reliable Transport
Delivery Guarantees & NVS Offline Mailbox

2.4 GHz RF is inherently noisy. Walls, foliage, and distance cause dropped packets. To provide a chat experience that feels as reliable as Signal or iMessage, I engineered a robust delivery and store-and-forward system:

End-to-End ACKs
Unicast messages require an explicit cryptographic ACK from the destination node routed back to the sender.
Exponential Backoff
Unacknowledged packets retry up to 3 times with exponential backoff (500ms initial timeout) before reporting failure.
NVS Offline Mailbox
Stores up to 16 packets in flash for temporarily unreachable nodes, holding them for up to 30 minutes until the node re-appears.
64-Message History
RAM ring buffer caches recent channel history so phone apps receive instant message catch-up upon BLE reconnection.

Users see real-time checkmarks in the mobile interface: single check for mesh transmission, double check for verified delivery.

06 Mobile Companion
Bridging Silicon to Smartphones: iOS, macOS & Android

I didn't want MeshOS to be a project that lived exclusively in a serial terminal or UART console. If a communication tool isn't convenient on a real phone, nobody will use it in a real emergency.

I wrote native companion applications for both major mobile platforms:

Apple Ecosystem: SwiftUI & Metal
Universal app for iOS and macOS built with Swift and CoreBluetooth. Features an interactive force-directed mesh topology visualizer rendered on the GPU using Apple Metal shaders.
Android: Jetpack Compose & Coroutines
Modern Android client built with Kotlin, Jetpack Compose, and Material You design. Runs a foreground Bluetooth service to maintain continuous background message reception.

The ESP32 advertises a custom BLE GATT service (DECAFBAD-CAFE-4BEE-B00B-000000000000). When you tap send on your iPhone, the message streams over BLE with 512-byte MTU buffers, enters the ESP32 mesh router, hops over 2.4 GHz radio, and pops up as a native notification on the recipient's phone.

07 Voice & Files
Chunked Files, Voice Notes & Live Telemetry

Text is essential, but voice and situational imagery save lives. ESP-NOW has a hard payload limit of 250 bytes per frame, so sending binary media required building an application-layer segmentation and reassembly protocol:

Chunked File Transfer
Splits files up to 4KB into 200-byte chunks. Includes a selective retransmission bitmap so only dropped chunks are re-sent.
3-Second Voice Notes
Compresses short voice recordings into lightweight audio frames transmitted across hops and played back inside the companion app.
Live RSSI & Ping RTT
Calculates real-time link quality indicators (RSSI dBm) and measures round-trip time across active routing paths.
Battery Telemetry
Nodes append LiPo battery percentage, heap memory stats, and uptime into periodic heartbeat discovery frames.

The topology graph in the app tints node badges green, yellow, or red based on live battery levels and radio signal strength, making node placement in the field effortless.

08 Time Sync & OTA
Distributed Mesh Clock Sync & BLE OTA Updates

Without internet or GPS, nodes have no access to Network Time Protocol (NTP) servers. However, cryptographic nonces, message timestamps, and offline mailbox expiries require synchronized clocks.

I built a distributed stratum-based time synchronization algorithm: nodes announce their clock stratum and uptime during heartbeat beacons. When a node connects to a smartphone over BLE, it absorbs real-world epoch time and propagates it across the entire mesh, aligning node clocks within ±50 milliseconds.

WIRELESS BLE FIRMWARE UPGRADES
Upgrading nodes sealed in weatherproof enclosures is handled through dual-partition OTA (ota_0 and ota_1). The companion app streams signed binary chunks over BLE GATT with SHA-256 verification and automatic rollback protection.

If a flashed firmware image crashes during its first boot, the ESP-IDF bootloader detects the panic and reverts instantly to the previous valid partition.

10 Reflections
What Building MeshOS Taught Me

Building MeshOS was one of the most demanding engineering projects I've tackled because it refused to stay inside a single discipline.

In the morning, I would be debugging bit-level radio frame collisions and FreeRTOS task starvation with an oscilloscope and logic analyzer. By the afternoon, I was writing SwiftUI animations, tuning Metal shaders for force-directed graph physics, and handling Android Bluetooth lifecycle edge cases.

No central server. No cell tower. No monthly bill. Just nodes communicating with nodes.

It proved to me that we don't have to surrender our autonomy to massive cloud providers to stay connected. With thoughtful firmware architecture, hardware cryptography, and clean native software, a few pieces of inexpensive silicon can form an unbreakable communication lifeline.

VIBE CODING ACROSS FOUR PLATFORMS

Developing MeshOS spanned four disparate stacks: C/FreeRTOS firmware, SwiftUI on iOS/macOS, Jetpack Compose on Android, and PSA Crypto. I leveraged AI tools as a true vibe coder to rapidly brainstorm UI layouts, translate concepts across languages, and structure multi-platform documentation.

Crucially, the core network architecture—bounded TTL flooding, the 64-entry LRU ring buffer, inter-core FreeRTOS queue dispatching, AES-128-GCM hardware crypto, and Metal GPU shaders—was engineered and written by me. AI helped supercharge my brainstorming and documentation, but the system architecture and critical code were built by hand.
