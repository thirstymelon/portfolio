✦ Glyph Graphics Framework

Building a portable graphics framework for bare-metal Ada.

Embedded graphics are usually a story of compromises. Tiny displays have tiny framebuffers. Microcontrollers have limited memory. Communication with the display can be slower than the rendering itself. And unlike desktop systems, there is no operating system quietly taking care of memory management and hardware abstraction underneath the application.

I wanted to explore what a graphics framework could look like when built specifically around those constraints. That became Glyph — a lightweight, portable graphics framework written in Ada 2022 for bare-metal and embedded systems. Glyph is designed to remain independent of any BSP, HAL, SDK, or RTOS. The graphics core focuses purely on rendering, while framebuffer management, memory layouts, display controllers, and hardware transports remain separate layers. Development currently targets the Vicharak Shrike-Lite (RP2040) with an SSD1306 128×64 OLED over I²C.

Starting From Scratch

Glyph is both a framework and a learning project.

This is my first embedded graphics framework and my first time building the different pieces of a display stack from the ground up.

Instead of taking an existing graphics library and adapting it to Ada, I wanted to understand what actually goes into one. That meant exploring:

Graphics Primitives & Rasterization

Drawing pixels, lines, rectangles, and filled bounds with deterministic integer math.

Line Clipping Algorithms

Preventing memory corruption when drawing geometry beyond screen edges.

Framebuffer Representation

Managing bit-packed monochrome arrays with zero dynamic heap allocation.

Display Memory Layouts

Mapping screen coordinates to physical controller page layouts.

Display Controller Protocols

Translating commands, initialization sequences, and window bounds for the SSD1306.

Transport Abstraction

Decoupling rendering logic from I²C and SPI bus communication.

Ada Generics & Strong Types

Enforcing coordinate boundaries and preventing X/Y argument inversions at compile time.

Bare-Metal Software Architecture

Designing clean, isolated abstraction boundaries without relying on an OS.

The goal wasn't to build the biggest graphics framework possible. It was to understand the layers well enough to design them properly.

[ 02 ]

Why Ada?

One of the main reasons I started Glyph was the lack of graphics and display-driver infrastructure in the Ada embedded ecosystem.

For embedded C and C++, it is relatively easy to find libraries and drivers for common displays and controllers. In Ada, the selection is considerably smaller. If I wanted a reusable graphics framework that was truly Ada-native, I couldn't simply assume that all the pieces I needed already existed.

So I decided to build one.

That also made Glyph a useful way to explore how Ada's strengths could translate into embedded graphics: strong types, static memory, explicit interfaces, and predictable behavior.
[ 03 ]

The Architecture

I wanted the graphics engine to be completely unaware of the hardware it eventually renders to. So Glyph is split into a series of independent layers.

At the top is the Display abstraction, which brings the pieces together for an application. Underneath it are the Canvas, Framebuffer, Layout, Controller, and Transport layers.

Figure 1: Modular layers of the Glyph graphics pipeline

Each layer has a relatively small responsibility:

  • The graphics algorithms don't know what an SSD1306 is.
  • The framebuffer doesn't know how an I²C bus works.
  • The transport doesn't know anything about drawing lines.

That separation is what allows the core framework to remain portable.

[ 04 ]

A Small Problem With a Big Consequence

One of the first algorithms I implemented was line clipping.

It sounds like a small detail. It isn't.

When drawing on a fixed framebuffer, geometry can easily extend beyond the visible area. A renderer that blindly writes those pixels risks writing outside the framebuffer.

Glyph uses the Liang–Barsky algorithm to clip lines against the active drawing region before rasterization. The resulting line is then rasterized using Bresenham's integer line algorithm.

Line → Liang–Barsky → Bresenham → Pixel → Framebuffer

It's a small example of the philosophy behind Glyph: use well-defined algorithms and keep them independent from the hardware layer.

[ 05 ]

Keeping Memory Predictable

Another core decision was to avoid dynamic memory allocation.

Glyph uses statically composed framebuffer structures rather than relying on a heap. For the current 128×64 monochrome display, the framebuffer is only:

1024 Bytes

That makes the memory requirements straightforward and predictable. It also fits naturally with the kind of systems Glyph targets: small microcontrollers where deterministic resource usage is more important than the flexibility provided by dynamic allocation.

[ 06 ]

From Pixels to an OLED

The first physical target for Glyph is an SSD1306 128×64 OLED.

The graphics code doesn't directly talk to the SSD1306:

  • The framebuffer contains the pixels.
  • The layout determines how those pixels map into memory.
  • The SSD1306 controller layer understands the display.
  • And the transport layer handles communication with the hardware.

This keeps the graphics core independent from the actual display being used.

[ 07 ]

The First Proof

The first hardware test was deliberately simple. I wanted something that exercised the framework without hiding it behind a large application. A few primitives were enough:

Ada (Glyph Hardware Test Example) 
OLED.Initialize;
OLED.Canvas.Clear;

OLED.Canvas.Glow_Rectangle
  ((Min_Point => (X => 0, Y => 0),
    Max_Point => (X => 127, Y => 63)),
   On);

OLED.Canvas.Glow_Line (0, 0, 127, 63, On);
OLED.Canvas.Glow_Line (0, 63, 127, 0, On);

OLED.Canvas.Glow_Filled_Rectangle
  ((Min_Point => (X => 54, Y => 22),
    Max_Point => (X => 72, Y => 40)),
   On);

OLED.Render;

That's essentially the interface I wanted to reach: initialize the display, draw to the canvas, and render. The RP2040-specific transport and hardware setup stays outside the graphics API.

[ 08 ]

What Exists Today

Glyph already has the foundation of a small graphics stack:

Rendering Primitives

Pixel, line, rectangle, and filled-rectangle drawing routines.

Mathematical Line Clipping

Liang–Barsky line clipping against visible viewport boundaries.

Integer Rasterization

Bresenham line and rectangle rasterization algorithms.

Static Framebuffer

Zero-heap 1-bit packed memory structure (1024 bytes for 128×64).

Display Memory Layouts

Abstraction for horizontal, vertical, and page-oriented layouts.

SSD1306 Controller

Full initialization sequences and hardware controller support.

Transport Abstraction

Generic interfaces for I²C and SPI physical transmission.

Verified on Silicon

Reference application tested on physical Vicharak Shrike-Lite (RP2040).

[ 09 ]

What's Next?

The roadmap is intentionally incremental:

More Primitives

Circles, ellipses, and triangle rasterization.

Better Rendering

Partial updates, dirty regions, and more efficient framebuffer flushing.

More Hardware

Additional transports, display controllers, framebuffer layouts, and pixel formats.

Text & UI

Bitmap fonts, image rendering, and eventually lightweight embedded UI components.

[ 10 ]

What Glyph Means to Me

Glyph is still a relatively small project, but that's part of what makes it interesting.

I'm not trying to build a full desktop-style graphics stack for a microcontroller. I'm trying to understand how far a carefully designed, portable and strongly typed Ada framework can go on very constrained hardware.

The project has given me a reason to work across several layers at once — from rasterization algorithms and memory layouts to display protocols and bare-metal architecture.

And perhaps most importantly, it is helping fill a gap I encountered firsthand:

Building graphics for embedded systems in Ada shouldn't require leaving the Ada ecosystem whenever you want to put something on a screen.

Glyph is my attempt to make that a little easier.
