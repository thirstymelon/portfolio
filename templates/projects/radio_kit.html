PROJECT 03 · RF & CLOCK SYNTHESIS
Version 0.2.0 · RP2040

∿ Radio_Kit Framework

Turning an RP2040's clock tree into an experimental RF source.

What if an ordinary microcontroller could generate an RF carrier without a radio chip? That was the question behind Radio_Kit. The Raspberry Pi RP2040 doesn't have a conventional RF transceiver — no built-in Wi-Fi, Bluetooth, or dedicated radio peripheral. But while exploring its clock architecture, I found something interesting: the RP2040 has a surprisingly flexible clock-generation system, including PLLs, fractional dividers, and four dedicated General-Purpose Clock Outputs.

So instead of adding another chip, I decided to experiment with what the RP2040 could do by itself. The result is Radio_Kit — an experimental Ada framework that uses the RP2040's native clock hardware to generate programmable digital RF carriers directly on GPIO pins.

The Idea

Most embedded radio projects start with a radio.

You pick a transceiver such as an SX1262, CC1101, or nRF24L01, connect it over SPI, configure a frequency, and let the dedicated hardware handle the RF side.

I wanted to approach the problem from the opposite direction. Instead of asking:

"Which radio chip should I use?"

I asked:

"How much of a radio can I build from the hardware already inside the microcontroller?"

The RP2040's clock system turned out to be an interesting answer. A clock is, after all, a precisely timed digital signal. If that signal can be configured over a sufficiently wide frequency range and routed to a physical GPIO, it can also become the starting point for RF experimentation. That became the foundation of Radio_Kit.

[ 02 ]

A Radio Without a Radio Chip

The core of the project is remarkably simple. The RP2040 starts with its 12 MHz crystal oscillator, which feeds the chip's clock-generation system. I configure PLL_SYS to produce a 90 MHz reference, then route that clock into one of the RP2040's dedicated GPOUT channels.

The GPOUT peripheral contains an 8-bit integer and 8-bit fractional divider. By controlling that divider, the 90 MHz reference can be converted into a much lower programmable frequency.

Conceptually: 12 MHz XOSC → PLL_SYS → 90 MHz → GPOUT Divider → GPIO → Carrier

That small piece of silicon is essentially the heart of Radio_Kit.

[ 03 ]

From 6 Hz to 90 MHz

One of the most interesting aspects of this approach is the frequency span. The current implementation targets carrier generation from approximately 6 Hz up to 90 MHz. That is an enormous range for what is fundamentally a clock-output experiment.

At the lower end, the same mechanism can be used for extremely slow timing signals. At the upper end, the output enters the RF range and can be observed with appropriate test equipment.

The important detail is that this isn't an analog RF synthesizer. The RP2040 is producing a digital clock waveform, not a perfectly sinusoidal carrier. Consequently, the output contains harmonic components that become increasingly important as the signal frequency increases. That limitation is actually part of what makes the project interesting.

[ 04 ]

Making the Hardware Feel Like Ada

The other half of the project is the software. Radio_Kit is written in Ada 2022, and I didn't want the framework to simply expose a collection of register-writing procedures.

The goal was to create an abstraction where the application thinks about the hardware in terms of resources and intent. For example, the application should be able to say:

"Generate a carrier at this frequency on this GPIO."

It shouldn't have to know which internal GPOUT channel corresponds to that GPIO, which clock multiplexer needs to be selected, or which divider registers need to be modified. Radio_Kit handles those details underneath the API.

Ada's type system also provides an interesting advantage here. Frequency values can be constrained to the supported range, allowing invalid values to be rejected at the interface rather than being blindly passed into low-level clock calculations.

This was an important part of the experiment for me: Can low-level hardware experimentation still have a clean, strongly typed software interface? Radio_Kit is my attempt at answering that.

[ 05 ]

Four Outputs Hidden in the Silicon

The RP2040 provides four GPOUT channels, exposed through specific GPIO pins:

GPIO Pin Silicon Clock Output
GPIO21 GPOUT0
GPIO23 GPOUT1
GPIO24 GPOUT2
GPIO25 GPOUT3

I chose to make the public API GPIO-oriented rather than exposing GPOUT0, GPOUT1, and so on. That small design decision makes the framework considerably more intuitive.

From the application's perspective, the physical hardware is what matters: "Use GPIO21." The framework takes care of translating that into the appropriate silicon resource.

[ 06 ]

The First Carrier

The first milestone for Radio_Kit was intentionally simple:

Generate a stable, unmodulated carrier.
No modulation. No receiver. No protocol. No complicated signal processing.
Just a programmable carrier coming directly out of the RP2040.

That gave me a clean foundation for testing the clock configuration, frequency calculations, GPIO routing, and Ada resource model independently.

Ada (examples/basic_carrier/src/basic_carrier.adb) 
with Radio_Kit.Radio_Clock; use Radio_Kit.Radio_Clock;
with Radio_Kit.Types;
with RP.GPIO;

procedure Basic_Carrier is

   Config_21 : constant Radio_Kit.Types.Clock_Config_T :=
     (GPIO_Pin => (Pin => 21), Frequency => 90_000_000);

   --  Config_23 : constant Radio_Kit.Types.Clock_Config_T :=
   --    (GPIO_Pin => (Pin => 23), Frequency => 30_000_000);

   --  Config_24 : constant Radio_Kit.Types.Clock_Config_T :=
   --    (GPIO_Pin => (Pin => 24), Frequency => 20_000_000);

   --  Config_25 : constant Radio_Kit.Types.Clock_Config_T :=
   --    (GPIO_Pin => (Pin => 25), Frequency => 10_000_000);

   Radio_21 : Radio_T;
   --  Radio_23 : Radio_T;
   --  Radio_24 : Radio_T;
   --  Radio_25 : Radio_T;

begin
   Radio_21.Initialize (Config_21);
   --  Radio_23.Initialize (Config_23);
   --  Radio_24.Initialize (Config_24);
   --  Radio_25.Initialize (Config_25);

   Radio_21.Transmit;
   --  Radio_23.Transmit;
   --  Radio_24.Transmit;
   --  Radio_25.Transmit;

   loop
      null;
   end loop;
end Basic_Carrier;
[ 07 ]

The Catch: A Digital Signal Is Not a Clean RF Signal

There is an important distinction between generating a carrier and generating a useful radio signal.

A GPOUT output is a digital clock. That means the waveform contains the fundamental frequency along with harmonic energy. A carrier at f can therefore produce significant components around 3f, 5f, 7f, and other harmonics.

So simply connecting a wire to the GPIO and calling it an antenna isn't equivalent to having a proper RF transmitter.

For experimentation, the output should be treated as a digital RF source and measured accordingly. Filtering, attenuation, impedance, shielding, and appropriate test equipment become important depending on what is being investigated.

This is also why Radio_Kit is currently positioned as an experimental and educational project, rather than a replacement for a dedicated RF transceiver.
[ 08 ]

What I Have So Far

Version 0.2.0 is intentionally modest. It establishes the underlying carrier-generation mechanism and provides a clean Ada interface around it. At this stage, Radio_Kit can:

Broadband Carriers

Generate programmable carriers from approximately 6 Hz to 90 MHz.

Native Hardware

Use the RP2040's native PLL_SYS and GPOUT hardware directly.

4 Supported Output Pins

Output cleanly through GPIO21, GPIO23, GPIO24, and GPIO25.

Zero Additional RF Silicon

Generate carriers without an external RF synthesizer or transceiver IC.

The interesting part is that none of this requires additional RF silicon. It is all coming from the clock architecture that was already inside the RP2040.

[ 09 ]

What's Next?

Radio_Kit currently generates an unmodulated carrier. The next step is to make that carrier useful:

FM & FSK

Experiment with dynamically changing the divider to introduce frequency modulation and simple data transmission.

PIO & DMA

Investigate whether the RP2040's PIO and DMA hardware can provide more precise, high-speed frequency control.

RP2040-to-RP2040 Link

Eventually, use two RP2040 boards to experiment with a complete transmitter-to-receiver communication path.

[ 10 ]

Why I Built It

Radio_Kit isn't really about building a better radio. There are already excellent RF chips that do that far better.

What interested me was the boundary between a microcontroller and the hardware underneath it. The RP2040 is usually viewed as a dual-core microcontroller with GPIO, PWM, PIO, ADC, and timers. Its clock-generation system is rarely the first thing that comes to mind when thinking about RF experimentation.

I wanted to see what happens when you look at that hardware differently:

A PLL becomes a frequency source.
A clock divider becomes a programmable synthesizer.
A GPOUT pin becomes a carrier output.
And a few lines of strongly typed Ada become the interface between the software and the silicon.

That's what Radio_Kit is about: exploring what is possible when you stop treating the microcontroller as just a CPU and start treating the silicon itself as a toolbox.
